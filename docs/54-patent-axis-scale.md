## 3. 技術の説明（自己完結）

### 3.1 解こうとした問題

ペンとタブレットで 3D モデリングをするとき、**軸を 1 本だけ固定したスケール**
（「高さだけ 1.3 倍」など）は頻繁に要る。従来のやり方は 2 つで、どちらもタブレットでは辛い。

1. **ギズモのハンドルをつかむ**。画面上の数十 px の小さな箱を指で正確に掴む必要がある。
   指の腹はハンドルを隠すし、モデルが小さく表示されていると掴めない
2. **キーボードの軸キー**（Blender の `S` → `X` など）。タブレットにキーボードは無い

### 3.2 構成

A. **3 本指のジェスチャ**がビューポート上で選択物の変形に割り当てられている
   （カメラ操作ではない。カメラは 2 本指）

B. ジェスチャの中身（つまむ = スケール / 滑らせる = 平行移動 / ひねる = 回転）は
   **開始時に 1 つだけ決まり、途中で入れ替わらない**。決め方は、つまみ量・重心移動量・
   ひねり量を**同じ px の物差しに換算して最大のものを採る**

C. **画面上の修飾ボタン**（物理キーではない。片手で押さえられる位置にあり、
   押している間だけ有効 / 左へずらして離すとロック）が押されていると、
   つまみが**一様スケールから軸固定スケールに変わる**

D. **軸は 2 段の写像で決まる**

   1. **指の並びの向き**を画面上で測る。いちばん離れた 2 本を結ぶ線の傾きを、
      45° を境に **vertical / horizontal** のどちらかに倒す
   2. その vertical / horizontal を、**現在の参照枠**の 3 本のうち 1 本へ写す。
      写し方は枠の種類で変わる（下表）

| 参照枠 | horizontal（横につまむ） | vertical（縦につまむ） |
|---|---|---|
| ワールド | X と Z のうち**画面の右ベクトルに近いほう** | **Y**（固定） |
| オブジェクト / ローカル | 3 本のうち画面の右に近い 1 本 | 3 本のうち画面の上に近い 1 本 |
| 法線 | U と V のうち画面の右に近いほう | **N**（固定） |

E. **枠とカメラの向きはジェスチャ開始時に凍結**される。操作中にカメラが動いても、
   選択の法線が変わっても、軸は切り替わらない

F. 伸ばし方は、ピボットからの相対位置 `r` に対し

```
r' = r + (k − 1)(r · a) a
```

   （`a` = 選ばれた軸の単位ベクトル、`k` = 倍率）。倍率 `k` は
   `現在の指の広がり / 開始時の指の広がり`。広がりは**重心からの平均距離**で測るので、
   指 2 本でも 3 本でも同じ式になる。`k` には下限 0.02 を置いて裏返りを防ぐ

   オブジェクト全体が対象のときは、代わりにオブジェクトの `scale` の
   **該当成分だけ**に `k` を掛ける（枠がオブジェクト軸と一致しているため等価）

### 3.3 擬似コード

```
onGestureStart(pointers):
    if 選択なし: 何もしない（カメラにも化けさせない）
    frame  = 現在の参照枠（world | object | local | normal）を作る   # 凍結
    camera = { right, up, forward }                                  # 凍結
    basis  = cluster(pointers)                                       # 重心・広がり・並びの向き
    kind   = null

onGestureUpdate(pointers):
    now = cluster(pointers)
    if kind == null:
        pinch = |now.spread − basis.spread| × 2
        swipe = |now.center − basis.center|
        turn  = |回転角| × now.spread
        if max(pinch, swipe, turn) < 10px: return          # 不感帯
        kind = argmax(turn, pinch, swipe) の種類
        pinchAxis = now.axis                               # vertical | horizontal（凍結）

    if kind == scale:
        k = now.spread / basis.spread
        if 修飾ボタンが有効:
            a = selectAxis(frame, camera, pinchAxis)       # 上の表
            各点 r について  r += (k − 1)(r·a)a
        else:
            各点 r について  r *= k                         # 一様
```

### 3.4 実機で決めた数値

| 値 | 意味 |
|---|---|
| 10 px | 3 本指の不感帯。これを越えるまで種類を決めない |
| 45° | 指の並びを縦横どちらに倒すかの境 |
| 0.9 | 法線枠で U を作るとき「N とほぼ平行」と見なす内積のしきい |
| 0.02 | 倍率の下限（裏返り防止） |
| 400 ms | 3 本指の長押し（別機能へ分岐） |

## 4. ありふれている部分（新規性を主張できない）

正直に列挙する。ここを独立項に書くと間違いなく拒絶される。

1. **軸固定スケールそのもの**。Maya、3ds Max、Blender、Softimage に 1990 年代からある
2. **2 本指のつまみで拡大縮小**。iPhone OS（2007）以降、常識
3. **参照枠の切り替え**（ワールド / ローカル / 法線）。Maya の移動ツールの標準機能
4. **ギズモのドラッグ中に軸を凍結する**こと。主要 DCC ツールの標準挙動
5. **修飾キーで操作の意味を変える**こと。あらゆる DCC ツール
6. **マルチタッチで指の本数ごとに役割を変える**こと。多数の先行例
7. **指の並びの向きで縦横を判定する**こと自体。2D の写真編集アプリに非一様スケールの
   例がある可能性が高い（要調査）

## 5. 新しいかもしれない部分（差分の候補）

ここが争点になる。強い順に並べる。

### 候補 1（いちばん強いと思う）— 2 段写像 + 枠の凍結

> **画面上の指の並びの向き**という 2 値の入力を、
> **ユーザーが選んだ 3D 参照枠**（ワールド / オブジェクト / 法線）の中で
> **現在のカメラ姿勢から見て画面の右・上に最も近い軸**へ写し、
> **その写像をジェスチャ開始時に固定する**

ポイントは「画面の向き」と「3D の軸」の間に**カメラ依存の最近接選択**を挟んでいるところ。
単に「縦につまんだら Y」ではなく、**カメラをどう回していても、画面で縦につまめば
画面で縦に見えている軸が伸びる**。これにより、ユーザーは 3D の軸名を意識せずに
軸固定スケールができる。

### 候補 2 — 法線枠の例外規則

法線枠だけは最近接規則を使わず、**縦つまみを常に N（面の法線）に割り当てる**。
理由は、面がカメラを向いていると N は視線とほぼ平行になり、画面の上にも右にも乗らず、
最近接規則では N が選ばれなくなるため。**最近接規則の破綻を、用途から逆算して
例外で埋めている**という点に技術的な工夫がある。

### 候補 3 — 共通の物差しによる種類決定

つまみ・平行移動・ひねりを**同一の px 単位に正規化して最大値で 1 つに決め、以後固定する**。
特に、ひねりを `回転角 × 広がり`（指が描く弧の長さ）に換算して px と比較しているところ。

### 候補 4 — 画面上の保持型修飾子との組み合わせ

物理キーボードの無い環境で、**反対の手で押さえられる画面上の修飾ボタン**
（押している間だけ有効 / ずらして離すとロック / ペンの接近で合図が切れてもロックに退避）
を、一様スケールと軸固定スケールの切り替えに使う。

### 6.3 進歩性 — ここが本丸

審査官が立てそうな論理を先回りすると、こうなる。

> 引用例 1（タッチで非一様スケール。つまむ向きで軸を選ぶ 2D アプリ）に、
> 引用例 2（Maya 等の参照枠の切り替え）を組み合わせることは当業者に容易。
> 「画面の右に最も近い軸を選ぶ」ことは、画面操作と 3D 軸を対応づける際の
> 自明な設計事項にすぎない。

これに反論するなら、**候補 2（法線枠の例外）**がいちばん効く。
「最近接規則をそのまま適用すると、面がカメラを向いたときに法線軸が選べなくなる」という
**単純な組み合わせでは生じる不具合**があり、それを例外規則で解決している。
「組み合わせの阻害要因と、その解決」という進歩性の典型パターンに乗せられる。

ただし率直に言って、**候補 2 まで含めたクレームはかなり狭い**。
競合は「法線枠を実装しない」だけで回避できてしまう。

### 7-D. 私の推奨

**7-A を基本線にして、7-B は「このアプリを事業にする」と決めたときだけ**。

理由を正直に書く。

1. **回避が容易**。軸の選び方を「指の並び」ではなく「つまんだあとの移動方向」に
   変えるだけで、別の実装になる
2. **権利行使が現実的でない**。侵害の立証にはタッチ入力処理の内部を示す必要があり、
   個人で競合（Autodesk、Maxon、Nomad 等）を相手に争うのは割に合わない
3. **1 年半後に公開される**。すでに自分で全文公開しているので、
   秘密保持の利得はゼロ
4. **事業価値はここではない**。このアプリの価値は「タブレットで Maya 的モデリングと
   ZBrush 的スカルプトが両方できる」という総体にある。ジェスチャ 1 つの独占は、
   その価値をほとんど守らない

逆に、**出願する価値が出る条件**もある。

- 外部資金を入れる、または事業売却を考えている（特許の保有自体が交渉材料になる）
- この操作系を**ライセンス**する構想がある

## 10. クレーム素案（たたき台。弁理士が書き直す前提）

### 独立項（やや広め）

> タッチ面への複数の接触点を検出する工程と、
> 前記接触点の**配置方向**を画面座標上で判定する工程と、
> 三次元シーン内の選択対象について、**複数の参照枠から選択された一の参照枠**の
> 三本の軸を求める工程と、
> **仮想カメラの姿勢に基づき**、前記三本の軸のうち前記配置方向に対応する
> 画面方向に最も近い一の軸を**選択軸として決定**する工程と、
> 前記接触点の**広がりの変化量**から倍率を求める工程と、
> 前記選択対象の各点について、所定の基準点からの相対位置ベクトル `r` を
> `r + (k − 1)(r · a) a`（`a` は選択軸の単位ベクトル、`k` は前記倍率）に
> 変換する工程と、
> を備え、**前記参照枠および前記仮想カメラの姿勢は、前記接触の開始時点の値に固定**
> される、三次元形状の変形方法。

### 従属項の候補

1. 前記参照枠が**面の法線**に基づく枠である場合、前記配置方向が縦であれば
   最近接判定によらず**法線軸を選択軸とする**（＝候補 2）
2. 画面上に表示された**保持型の修飾操作子**が有効であるときに限り前記選択軸による
   変形を行い、無効であるときは等方的な変形を行う（＝候補 4）
3. 前記接触点の広がりが、**接触点の重心からの平均距離**として算出される
4. つまみ量・重心移動量・回転量を**共通の画面距離単位に換算**して比較し、
   最大のものに操作種別を決定し、以後当該接触が終了するまで変更しない（＝候補 3）
5. 前記倍率に下限値を設け、前記選択対象の反転を防ぐ
6. 前記配置方向が、最も離れた二つの接触点を結ぶ線分の傾きを 45 度で二値化して
   求められる
