# 09. 方向性レビュー（プロトタイプ 4 ラウンド後）

作成: 設計担当（Fable）。実装担当（Opus / Codex）はこの文書を、`04` `05` より優先して読むこと。

## 結論

大枠は合っている。差別化（マルチ解像度ブリッジ）、ネイティブ C++、Maya 語彙の採用、v1 を絞る方針は維持する。
ただしプロトタイプの 4 ラウンドで、以下の 3 つがズレた。

| ズレ | 何が起きたか | 影響 |
|---|---|---|
| **A. プロトタイプの目的が変質した** | 「操作感の検証」のはずが、エッジフロー、スムージング角度、Catmull-Clark、カメラ焦点距離と、**機能実装**が続いている | 検証にならず、捨てるはずのコードが肥大化。C++ への移植コストが毎ラウンド増える |
| **B. マウス前提のフィードバックだけで回っている** | 要望が「Alt+右クリック」「ホバー」「右クリック長押し」と PC 操作ばかり。ペンと指での検証結果がまだ一度も出ていない | 製品の前提（ペン=ツール、指=カメラ、片手で届く配置）が未検証のまま Maya クローンが育っている |
| **C. 差別化の核に工数がゼロ** | マルチ解像度ブリッジは設計文書と Codex 指示書があるだけで、着手されていない | 最大の技術リスクが最後まで残る。ここが通らなければ設計全体を見直すことになる |

そして、**未確認の前提**が 1 つある。この環境では 3D 描画を一度も確認できていない。**実機（iPad と PC）でビューポートが描画されているか**、ユーザーからの報告がない。ここが壊れていれば以降の議論は空回りになる。

## 提案 1: v1.0 を「iPad で Maya 相当のポリゴンモデリング」に絞り直す

ユーザーの実際の優先順位は、行動を見る限り**モデリングの Maya 互換**にある。それ自体が市場の空白であることを改めて指摘する。

- Nomad Sculpt、Forger: ポリゴン編集が弱い
- Shapr3D: CAD であってポリゴンモデラーではない
- Blender: iPad で動かない

**「Maya の手触りでポリゴンモデリングができる iPad アプリ」は、それだけで競合がいない。**

したがって v1.0 の構成を次のように改める。

| 版 | 内容 | 期間目安（1 人） |
|---|---|---|
| **v1.0** | モデリング（Maya 語彙）、OBJ / FBX / USD 入出力、独自プロジェクト形式 | 6〜8 か月 |
| **v1.5** | スカルプト + マルチ解像度ブリッジ（差別化の堀） | +5〜6 か月 |
| v2.0 | UV | |
| v3.0 | マテリアル | |

トレードオフ: 差別化の核が v1.5 に後ろ倒しになる。ただし、この核を持つ競合はこの数年現れていない。先に「使えるモデラー」を出してユーザーを掴む方が、リスクが小さい。

**ただし、マルチ解像度の技術検証（提案 3）は v1.0 の期間中に並行して済ませる。** 出荷順序を変えるだけで、リスク検証は前倒しのまま。

## 提案 2: プロトタイプを凍結し、実機で検証する

**これ以上プロトタイプに機能を足さない。** 現状で検証に必要なものは揃っている。

次にやるべきは実機テストで、以下を iPad + Apple Pencil で試し、感想を書き出す。

1. 指 1 本でタンブル、2 本でパンとズーム。誤爆はないか
2. ペンで頂点を 1 つ選べるか（当たり判定 22px は適切か）
3. F ボタン長押しでマーキングメニュー。400ms は長いか短いか
4. メニューの方向仮選択。デッドゾーン 30px は適切か。フリック即決定は使えるか
5. SHF ラッチ → 移動で押し出し。ラッチという概念は理解できるか
6. マルチカット。ホバーがない環境で「押している間の予測線」は成立しているか
7. 左のゲージを親指で操作できるか。縦の長さは適切か
8. 左下クラスタの SHF / F / CTL / ALT に指が自然に届くか
9. パネルのドラッグとドッキングが指でできるか
10. 縦持ち・横持ちで破綻しないか

**「PC でどう動くか」ではなく「ペンと指でどう感じるか」の報告が、このプロトタイプの唯一の成果物になる。**

## 提案 3: マルチ解像度の検証を JS で先に行う

Codex 指示書（`08`）は C++ + OpenSubdiv 前提だが、**アルゴリズムの検証は JS で今日できる。**

- プロトタイプには既に四角形メッシュ構造と Catmull-Clark がある
- 1000 四角形程度なら JS で対話的に動く
- 剛体変換不変性のテスト（`08` の V3）は Node で自動実行できる
- この環境で実行・検証できる（C++ は実機ビルドが必要で、ここでは検証できない）

手順: 接空間デルタの保持 → レベル 0 編集 → 上位レベル復元、を `prototype/` 内の別ファイルで実装し、Node のテストで V1〜V5 を通す。**通ったら、その JS を仕様として C++ に移植する。** 通らなければ、設計を見直す判断が数か月早まる。

これが「大枠を考える側」から「実装する側」への次の具体的な依頼になる。

## 提案 4: 「Maya の語彙、タブレットの文法」に切り分ける

「Maya クローンを作ってからタブレットに寄せる」は方針として正しいが、**何を Maya から持ち込み、何を持ち込まないか**を明示しないと、マウス操作がそのまま残る。

| 持ち込む（語彙） | 持ち込まない（文法） | 置き換え |
|---|---|---|
| コンポーネントモード、マーキングメニューの配置、ツールの意味、F8–F11 / 4–7 のキー | Alt + 3 ボタンのカメラ | 指ジェスチャ |
| ソフト選択、マニピュレータの見た目と軸の色 | ホバー依存の表示（予測線、ハイライト） | 押している間に表示、離して確定 |
| オプションの文脈依存 | 修飾キー同時押し | ラッチ。ただし**ラッチが必要な操作を減らす**設計が本筋 |
| 選択色 | 右クリック | 長押し、または専用ボタン |

マーキングメニューは例外的に**タブレット向きの Maya 操作**である。方向で選ぶ操作はタッチと相性が良く、Maya 由来でありながらそのまま文法に採用できる。

## 提案 5: 指だけの操作を「ヒットテスト」で成立させる

現状は「指でツール」トグルで切り替えているが、目標は「指のみでの快適な操作」なのでトグル自体が負けである。

Nomad Sculpt の解を採用する。**指がメッシュの上にあればツール、何もない場所ならタンブル。** 判定はタッチ開始時のレイキャスト 1 回で済み、トグルが不要になる。2 本指は常にカメラ。ペンは常にツール。

## 提案 6: 引き継ぎの契約を文書に戻す

「Fable が大枠、Opus が実装」の分業では、**両者の間の契約は文書**でなければならない。現状、確定した挙動の多くが JS の中にしかなく、`04` `05` は古い。

ルール: プロトタイプで確定した挙動は `docs/10-interaction-spec.md`（新設）に**挙動として**書く。C++ の実装は JS ではなくこの仕様書から行う。JS は参照実装であって仕様ではない。

### 実装基盤の再検討（提案 7）

**前提が 2 つ変わったので、v1.0 の実装基盤を Web に切り替えることを提案する。**

1. v1.0 はモデリング特化になった。ネイティブ C++ を選んだ最大の理由は「数百万ポリゴンのスカルプトでメモリを完全に制御する」ことだった。ポリゴンモデリングで扱うのは数万〜十数万面で、**その理由が v1.0 には当てはまらない**
2. C++ のビルド環境が無い。さらに iOS のネイティブビルドには Mac と Xcode が必須で、PC が Windows なら iPad 向けの C++ は**そもそもビルドできない**

一方で、Web 版は今すぐ iPad mini と MovinkPad の両方で動く。ペン入力（筆圧・傾き・ペン判定）は Safari も Chrome も PointerEvents で取れる。WebGPU は iOS 26 の Safari で使える。ポリゴンモデリング程度のメモリなら Safari の制限にも収まる。**そして Opus が書いた変更を、数分後にタブレットで触って確かめられる。** C++ では、書いたコードを誰も実機で動かせないまま積み上がるリスクが大きい。

| 版 | 基盤 | 理由 |
|---|---|---|
| **v1.0 モデリング** | **Web（TypeScript + WebGL2 / WebGPU）**。PWA として配布し、ストア配布は Capacitor で包む | 今ある機材で今日から検証できる。メモリ要件が軽い |
| v1.5 スカルプト + マルチ解像度 | ジオメトリカーネルを C++ で書き wasm にする。メモリ上限に当たったら、そのカーネルをそのままネイティブに持ち出す | 差別化の核は C++ で書き、Web とネイティブの両方で使える形にしておく |

以前「Web は本体に不適」と書いたのは、スカルプトのメモリ要件を前提にした判断だった。前提が変わったので判断も変える。ネイティブ C++ の設計文書（`02`）は v1.5 以降の参照として残す。

これに伴い、プロトタイプは「使い捨て」ではなく**製品の種**になる。ただし今の 2400 行の単一ファイルは製品構造ではない。次の実装依頼は、機能追加ではなく **TypeScript + モジュール分割 + テストへの再構成**（ジオメトリカーネルを UI から分離する原則は `02` と同じ）。

### 指の扱いを変更した

「指でツール」トグルを廃止し、ヒットテストにした。指がメッシュかマニピュレータの上ならツール、外ならタンブル。トグルは「指はカメラ専用」の逆向きに残した。**矩形選択は指では始められない**（外で始めるとタンブルになる）。ここは実機で感触を確かめてから決める。

## 確定した判断

**v1.0 の実装基盤は Web（TypeScript + WebGL2 / WebGPU）で確定。** PC が Windows なので iOS ネイティブは組めず、Web が唯一の「今ある機材で iPad に届く」道でもある。

**スカルプト版への道は次の形で確保する。** これが「対応できるなら OK」への回答。

| 段階 | 形 | 上限の目安 |
|---|---|---|
| v1.5 スカルプト（Web 内） | ジオメトリカーネルを C++ で書き、wasm にして同じ Web シェルに載せる | iPad の Safari で使えるメモリ約 1GB 前後。**50 万〜100 万ポリゴン級**。Nomad Sculpt 相当で、ZBrush の数百万級ではない |
| その先（必要なら） | 同じ C++ カーネルをネイティブに持ち出す。Android は Windows から NDK でビルドできる。iOS は Mac が要るが、GitHub Actions の macOS ランナーなど CI 上の Mac でビルドできる | 数百万ポリゴン級 |

**カーネルを最初から C++ で書き、UI から切り離しておく**ことが条件。ここを守れば、Web 版とネイティブ版で同じコードが使える。逆に、JS でスカルプトを書いてしまうと、ネイティブに持ち出すときに全部書き直しになる。`02` の「core/ を非依存に保つ」原則はそのまま生きる。

**配布**: まず PWA（ホーム画面に追加。Mac 不要）。App Store に出すときは Capacitor で包み、CI 上の Mac でビルドする。

### 実機で出た不具合と対処

| 症状 | 原因の見立て | 対処 |
|---|---|---|
| ツール UI が消える | ツール列のドック幅を `:has()` と内容依存サイズに任せていた。Safari は縦フレックス容器の固有幅を 0 に計算することがある | JS でクラスを付け、幅を 63px に明示 |
| 長押しで Web の長押し機能が働く | ポインタイベントだけでは iOS の長押し（選択・コールアウト・拡大）を止めきれない | 長押しを受ける要素（ビューポート、F ボタン、ツール列、アウトライナ行、ゲージ、メニュー）で `touchstart` を明示的に抑止。`click` に頼るボタンには付けない |
| ホームインジケータと重なる可能性 | 全画面時のセーフエリア未考慮 | 左下クラスタと HUD にセーフエリア分の余白 |

**注意**: claude.ai のアーティファクト画面の中で開いている場合、長押しは claude.ai 側の UI に取られる可能性がある。そちらは直せない。GitHub Pages（単体ページ）で開いて再確認すること。

## 次の実装依頼（Opus 向け）

順番はこのとおり。**1 が済むまで 2 以降に手を付けない。**

1. **実機で再確認**（ユーザー）: GitHub Pages で開き、ツール列が出るか、長押しでマーキングメニューが出るか
2. **再構成**: 単一 HTML を TypeScript + Vite + モジュールに分割。`core/`（メッシュ、プリミティブ、トポロジ編集、Catmull-Clark。DOM も Three.js も参照しない）と `app/`（描画、入力、UI）に分ける。`core/` に doctest 相当（vitest）を付け、`08` の V1〜V6 を JS で通す土台にする
3. **マルチ解像度の検証**（`08` を JS で）: 接空間デルタの往復。剛体変換不変性のテストを vitest で自動化
4. モデリング v1.0 の残り機能（ベベル、ブリッジ、マージ等）は 3 の後

ユーザーの実機テスト結果は、この文書の末尾に追記していく。
