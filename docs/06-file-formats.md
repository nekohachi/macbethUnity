
# 06. ファイル形式対応

ご要望の 4 つ（`.mb` / `.obj` / Substance ファイル / `.fbx`）について、実現可能性を率直に評価します。**そのうち 2 つは実質的に不可能です。** 代替案を含めて説明します。

## 6.1 ご要望の形式の評価

| 形式 | 読み込み | 書き出し | 判定 |
|---|---|---|---|
| `.obj` | ○ | ○ | 問題なし。自前実装で十分 |
| `.fbx` | ○ | ○ | 可能。ただし Autodesk 公式 SDK は使えない（後述） |
| `.mb`（Maya Binary） | ✕ | ✕ | **不可能。`.ma` で代替** |
| Substance（`.sbsar` / `.spp` / `.sbs`） | ✕ | ✕ | **不可能。テクスチャ書き出しで代替** |

---

## 6.2 `.mb` が不可能な理由と代替案

`.mb` は Autodesk の完全非公開バイナリ形式です。仕様書は公開されておらず、読み書きする唯一の正式手段は Maya の C++ API（devkit）ですが、これは **Maya 本体がインストールされライセンス認証された環境でしか動作しません**。タブレット上で `.mb` を読むことは原理的にできません。

### 代替案: `.ma`（Maya ASCII）に対応する

`.ma` はテキスト形式で、実体は MEL コマンドの列です。

- **書き出し（推奨・実装可能）** — メッシュ、トランスフォーム、UV、クリース、シェーダ割り当てを含む `.ma` を出力するのは十分に実装可能です。Maya 側で普通に開けます
- **読み込み（限定的）** — MEL コマンド列を完全に解釈するのは事実上インタプリタを書くことになるため非現実的です。`createNode transform` / `createNode mesh` / `setAttr` に限定した**サブセットパーサ**なら実装できます。ただし複雑なシーンでは失敗します

### ユーザーへの案内

`.mb` が必要な場合は Maya 側で変換してもらいます。この 1 行で済みます。

```mel
file -force -type "mayaBinary" -save;
```

ドキュメントやアプリ内ヘルプに、この変換手順を明記してください。**「.mb 非対応」ではなく「.ma 経由でご利用ください」と案内するのが正しい伝え方です。**

## 6.3 `.fbx` の実装方針

**Autodesk FBX SDK は使えません。** 公式にサポートされるプラットフォームは Windows / macOS / iOS / Linux で、**Android は対象外**です。片方だけ対応というわけにいかないので、サードパーティ実装を採用します。

### 読み込み: ufbx を使う

**[ufbx](https://github.com/ufbx/ufbx)（MIT ライセンス／パブリックドメイン）** を推奨します。

- `ufbx.h` と `ufbx.c` の 2 ファイルだけ。C99 で書かれた完全に可搬なコードで、iOS も Android も無改造でビルドできます
- FBX 3000 以降のバイナリ版・ASCII 版の両方に対応
- 公式 SDK との機能的な同等性を目標に開発されており、Blender の FBX インポータも ufbx への移行が進んでいます。実績として十分です

### 書き出し: 自前実装

ufbx は読み込み専用なので、書き出しは自前で書きます。FBX 7.4 バイナリの構造（ノードレコードのツリー、プロパティの型タグ、zlib 圧縮された配列）は解析され尽くしており、実装は可能です。メッシュ、法線、UV、マテリアル、階層構造に絞れば現実的な工数です。

**注意:** Blender の FBX エクスポータは GPL なので、コードを参照・流用しないでください。形式の仕様に基づいて独自に実装してください。

### FBX で必ずハマる落とし穴

パイプライン系のバグはほぼここに集中します。最初から対処してください。

| 項目 | 問題 |
|---|---|
| **軸方向** | Maya と ZBrush は Y-up 右手系、Unreal は Z-up、Unity は左手系。**本アプリの内部規約を Y-up 右手系に固定**したうえで、FBX ヘッダの `UpAxis` / `FrontAxis` / `CoordAxis` を必ず読み書きする |
| **単位** | Maya の既定はセンチメートル、glTF と USD はメートル。`UnitScaleFactor` を尊重し、内部単位を 1 つに決める |
| **UV の V 方向** | OBJ、FBX、glTF で V の向きが異なる。反転規則を入出力層の 1 箇所に集約する |
| **法線** | 明示的な法線とスムージンググループの両方が存在しうる。**往復しても法線が変わらないこと**をテストで担保する |
| **ノーマルマップの緑チャンネル** | Maya / Substance は OpenGL 形式（+Y）、Unreal は DirectX 形式（−Y）。**設定で切り替えられるようにする**。これは実務で最も多い事故です |

## 6.4 Substance が不可能な理由と代替案

`05-modes.md` にも書きましたが、改めて整理します。

| 形式 | 内容 | 状況 |
|---|---|---|
| `.sbsar` | 実行可能なパラメトリックマテリアル | Adobe の Substance 3D Materials SDK が必要。**商用ライセンス契約が要り、モバイル対応の可否は Adobe との個別交渉**になります |
| `.sbs` | Substance Designer のソース（XML） | XML なので開けはしますが、中身はノードグラフであり、各ノードの演算内容は Adobe 独自です。再現には結局エンジンが要ります |
| `.spp` | Substance Painter のプロジェクト | 非公開形式。正式な読み込み手段なし |

### 現実的な代替案（これで実務上ほぼ困りません）

1. **ベイク済みテクスチャセットの読み込み** — Substance Painter からの書き出しは PNG / TGA / EXR です。命名規則（`$mesh_$textureSet_BaseColor` など）を認識して自動でチャンネルに割り当てる機能を作れば、ユーザー体験としては「Substance のマテリアルを読み込めた」のとほぼ同じになります。**これを v1 で実装してください**
2. **MaterialX（`.mtlx`）を採用** — マテリアルグラフのオープン標準です。Adobe も Autodesk も対応しており、本アプリのマテリアル交換形式としてはこれが正解です
3. **glTF の PBR マテリアル** — シンプルなマテリアルならこれで往復できます

## 6.5 追加で対応すべき形式（ご質問への回答）

ご要望以外に必要な形式を、優先度順に挙げます。

### 最優先で入れるべきもの

**`.usd` / `.usdc` / `.usda` / `.usdz`（Universal Scene Description）**

**これが本アプリにとって最も重要な形式です。** 理由は 3 つあります。

1. **細分割とクリースをネイティブに表現できる唯一の主要形式です。** `UsdGeomMesh` は `subdivisionScheme = "catmullClark"`、`creaseIndices` / `creaseLengths` / `creaseSharpnesses`、`cornerIndices` / `cornerSharpnesses` を持ちます。**本アプリのマルチ解像度ワークフローと完全に一致します。** FBX も OBJ もクリース情報を正しく持てません
2. **iOS ネイティブ対応。** `.usdz` は Apple の標準形式で、Quick Look でそのまま閲覧・共有できます。作品の共有機能として強力です
3. **業界の標準がここに移りつつあります。** Maya は USD プラグイン、Substance も USD 書き出しに対応済みです

実装は、フル OpenUSD ライブラリはモバイルには重いので（数十 MB）、**[TinyUSDZ](https://github.com/lighttransport/tinyusdz)（MIT / Apache）などの軽量実装**か、必要な範囲に絞った自前の読み書きを推奨します。

### 高優先度

| 形式 | 用途 |
|---|---|
| **`.glb` / `.gltf`** | Web・モバイル標準の交換形式。PBR マテリアル込みで軽量。**共有・プレビュー用の既定書き出し形式にすべき**です |
| **`.mtl`** | OBJ の相方。必ずセットで対応 |
| **`.exr`（OpenEXR）** | 16bit / 32bit のディスプレイスメントマップ、HDRI 環境光。ライブラリは **TinyEXR（BSD）** |
| **`.hdr`（Radiance）** | HDRI 環境光。実装が簡単 |
| **`.png` / `.tga` / `.jpg` / `.tiff`** | テクスチャ入出力全般 |
| **独自プロジェクト形式（例 `.mbz`）** | **v1 から必須。** ZIP コンテナに JSON マニフェスト＋バイナリブロブ（メッシュ、サブディビジョンレベルのデルタ、レイヤー、マスク、テクスチャ）。**必ずバージョン番号を最初から入れてください。**後から追加するのは地獄です |

### 中優先度

| 形式 | 用途 |
|---|---|
| **`.abc`（Alembic）** | 高ポリメッシュのキャッシュ。Maya も ZBrush も対応。ライブラリは BSD だが HDF5 依存で重い。v2 以降で |
| **`.ply`** | 3D スキャンデータ、頂点カラー付きメッシュ。実装が簡単で対応価値あり |
| **`.stl`** | 3D プリント用途。実装がごく簡単で、ユーザーからの要望が確実に来ます |
| **`.mtlx`（MaterialX）** | マテリアル交換。マテリアルモード実装時に |
| **`.psd`** | レイヤー付きテクスチャの Photoshop 往復。書き出しのみでも価値あり |

### ZBrush との連携について

ZBrush の `.ztl` / `.zpr` も非公開形式で読めません。ただし **ZBrush 側が OBJ / FBX / Alembic を読み書きできるので、実務上これで困りません。**

補足として、OBJ の `g`（グループ）タグは ZBrush のポリグループに対応します。**OBJ の入出力でポリグループを保持するようにしてください。** ZBrush ユーザーにとって重要度が高い割に実装が軽い、費用対効果の良い対応です。

さらに踏み込むなら、ZBrush の **GoZ 形式**は解析が進んでおり、オープンな実装も存在します。ZBrush ユーザー向けの目玉機能になりえますが、優先度は v2 以降で十分です。

## 6.6 ファイルアクセスの実装（見落としやすい点）

形式のパーサだけでは足りません。**タブレットではファイルの「場所」を扱うのが難物です。**

- **iOS**: `UIDocumentPickerViewController` とセキュリティスコープ付き URL。iCloud Drive 連携。ファイルアプリからの「このアプリで開く」対応
- **Android**: Storage Access Framework（SAF）。Android 10 以降は直接のファイルパスアクセスが原則できません
- ネイティブ C++ なので、iOS は Objective-C++ から、Android は JNI 経由で直接扱えます。SAF だけは Java 側のコードが避けられません

もう 1 点。**大きなファイルの読み込みでメモリ不足による強制終了が起きます。** 500MB の FBX を一括で読むと確実に落ちます。ストリーミング読み込みと、読み込み前のファイルサイズ確認・警告表示を実装してください。

## 6.7 まとめ: 実装順序

| 段階 | 形式 |
|---|---|
| **v1.0** | `.obj` ＋ `.mtl`、`.fbx`（読み書き）、独自プロジェクト形式、`.png` / `.tga` / `.jpg` |
| **v1.1** | `.usdc` / `.usdz`、`.glb`、`.exr` / `.hdr`、`.stl`、`.ply` |
| **v1.5** | `.ma` 書き出し、`.ma` 限定読み込み、OBJ のポリグループ対応 |
| **v2.0** | `.abc`、`.mtlx`、`.psd`、GoZ |
| **交渉次第** | `.sbsar`（Adobe とのライセンス契約が前提） |
| **対応しない** | `.mb`、`.spp`、`.sbs`、`.ztl`、`.zpr` |
