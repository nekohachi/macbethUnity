# 02. 技術スタックとアーキテクチャ

## 2.1 エンジン選定: ネイティブ C++

**決定: ゲームエンジンを使わず、C++ で自作します。**

本アプリは**メモリ律速**のアプリケーションです。サブディビジョンレベルを 1 つ上げるとメモリが 4 倍になり、Undo 履歴が加わり、テクスチャが加わります。ここを 1 バイト単位で制御できるかどうかが、実現可能なポリゴン数を直接決めます。ゲームエンジンの管理ヒープと GC の上でこれを行うのは、可能ではあっても最適ではありません。

### この選択で得られるもの

| 項目 | 内容 |
|---|---|
| **メモリの完全な制御** | サブディビジョンレベルごとのアリーナアロケータ、正確な予算管理。Android の強制終了対策として決定的 |
| **GC 停止がゼロ** | iPad の 120Hz を維持するにはフレーム時間の一貫性が必要。管理言語では原理的に保証できない |
| **ライブラリとの言語一致** | OpenSubdiv、ufbx、xatlas、TinyEXR、TinyUSDZ はすべて C/C++。マーシャリング境界が消える |
| **プラットフォーム API への直接アクセス** | `coalescedTouches`、`predictedTouches`、`UIPencilInteraction`、`MotionEvent` にブリッジなしで到達できる。`04-input-ui.md` の要件がそのまま実装できる |
| **バイナリサイズと起動時間** | エンジン製の 1/3 程度。起動が速いことは制作ツールとして効く |
| **外部要因からの独立** | エンジンのライセンス変更、バージョンアップによる破壊、サポート終了の影響を受けない |

### この選択で失うもの（正直に）

エンジンが無料で提供していたものを、すべて自分で作ることになります。

- レンダラ、シェーダのビルドパイプライン
- **UI フレームワーク（最も過小評価されるコスト。後述 2.7）**
- アセットのビルドと配置
- クロスプラットフォームのビルドシステム
- クラッシュレポート、プロファイリング、ホットリロード

**v1.0 到達までの期間は、エンジン利用と比べておよそ 1.5〜2 倍になります。** `07-roadmap.md` に改訂した見積もりを記載しました。この差を受け入れる価値があるのは、本アプリが「メモリと入力遅延がそのまま製品価値になる」タイプのアプリだからです。逆に言えば、その 2 点を軽視するなら、この選択は割に合いません。

### 前提となるスキル

この路線は **C++ とグラフィックス API の実務経験を前提とします。** 経験がない状態で選ぶと、節約したはずのコストを何倍にもして払うことになります。ここは自己評価を正確に行ってください。

## 2.2 レイヤ構成

依存の向きを一方向に保ちます。下位層は上位層を知りません。

```
platform/        iOS(Objective-C++) / Android(NDK) / Win / macOS
  ├ 入力イベント、ファイルアクセス、ライフサイクル、システム UI
gfx/             レンダリング抽象（Metal / Vulkan）
core/            ★ プラットフォーム非依存・グラフィックス非依存
  ├ geometry/    メッシュ、細分割、マルチ解像度、ブラシ演算
  ├ document/    シーングラフ、Undo、プロジェクト保存
  └ io/          ファイル形式の読み書き
app/
  ├ render/      描画チャンク管理、シェーダ、マットキャップ、PBR
  ├ input/       ジェスチャ調停、ペン/指/マウスの抽象化
  ├ ui/          パネル、ドッキング、サークルメニュー
  └ modes/       モデリング / UV / スカルプト / マテリアル
```

**`core/` は最重要の資産です。** ここに OS 依存もグラフィックス依存も一切入れないでください。得られるもの:

- ユニットテストがデスクトップ上で高速に走る
- コマンドラインのテストハーネスで、実機なしにマルチ解像度の検証ができる
- 将来 wasm にビルドして Web ビューアを作れる（`06` で議論した軽量ビューア路線）
- グラフィックス API を差し替えても影響を受けない

## 2.3 レンダリング抽象の選定

Metal と Vulkan を直接両方書くのは、小規模チームには重すぎます。抽象層を挟みます。

| 候補 | ライセンス | 評価 |
|---|---|---|
| **bgfx** | BSD-2 | **推奨。** Metal / Vulkan / GLES を網羅、コンピュートシェーダ対応、モバイル実績が豊富。CMake で組み込め、ビルドの手間が小さい |
| **Dawn**（WebGPU 実装） | Apache-2.0 | 有力。API が現代的でコンピュート中心。**同じコードが後で Web に出せる**のが利点。ただし depot_tools を使うビルドが重く、iOS 対応の手間がある |
| Diligent Engine | Apache-2.0 | 機能豊富だが本アプリには過剰 |
| Metal / Vulkan 直書き | — | 制御は最大。工数も最大 |

**v1 は bgfx を推奨します。** 統合リスクが最も低く、実績があります。Web ビューアを戦略的に重視するなら Dawn を選ぶ判断もありえます。

ただし `gfx/` の内側に閉じ込めて、**後から差し替えられるようにしてください**。抽象層をアプリ全体に漏らさないことが条件です。

補足として、ジオメトリシェーダは使わないでください。Metal に存在しません。

## 2.4 メッシュデータ構造

ハーフエッジ構造は理論的には美しいのですが、**モバイルではメモリ効率とキャッシュ効率が悪すぎます**。採用しないでください。

用途で 2 つに分けます。

### 編集用（モデリングモード、低ポリ）

構造体の配列ではなく、配列の構造体（SoA）で持ちます。

```cpp
struct EditMesh {
    Array<float3>  positions;    // 頂点座標
    Array<int32>   faceOffsets;  // 面 i の頂点が faceCorners のどこから始まるか
    Array<int32>   faceCorners;  // 面を構成する頂点インデックス列
    Array<float2>  cornerUV;     // コーナー単位の UV（頂点単位ではない）
    Array<half>    edgeCrease;   // エッジのクリース値
};
```

隣接情報（頂点から接続面、エッジ一覧）は**派生データ**として CSR 形式で別途構築し、トポロジ変更時のみ再構築します。常時保持しないのがポイントです。

### スカルプト用（高ポリ、トポロジ固定）

トポロジが変わらないので、平坦な配列と空間分割で十分です。

```cpp
struct SculptMesh {
    Array<float3> positions;
    Array<float3> normals;
    BVH           bvh;        // 三角形クラスタ単位（Blender の PBVH 相当）
};
```

**BVH のリーフ単位で「汚れフラグ」を持つことが性能の鍵です。** ブラシストロークで触れたリーフだけを再計算し、GPU にも部分アップロードします。全メッシュを毎フレーム再アップロードすると、100 万ポリで即座に破綻します。

## 2.5 メモリ管理

ネイティブを選んだ最大の理由なので、設計を最初に固めます。

- **アリーナアロケータをサブシステム単位で持つ。** サブディビジョンレベルごと、Undo 履歴ごと、テクスチャごとに独立したアリーナを割り当てる
- **予算を定数として定義し、実行時に監視する。** `01-concept-scope.md` の端末別上限を使う
- **予算超過時の縮退動作を実装する。** 上位サブディビジョンレベルの自動破棄、Undo 履歴の切り詰め、テクスチャ解像度の低下。無言でクラッシュさせない
- **グローバルな `new` / `delete` をホットパスで使わない。** ブラシ適用や細分割の内側でのアロケーションはゼロにする
- 起動時にメモリ使用状況を表示する開発用オーバーレイを作る

Android では、システムからのメモリ逼迫通知（`onTrimMemory`）を受けて能動的に解放してください。ここを実装しないと強制終了が避けられません。

## 2.6 並列化と SIMD

- **ジョブシステム**を自作するか、`enkiTS`（zlib ライセンス）を使う。ブラシ適用、法線再計算、細分割はいずれも並列化しやすい
- **ARM NEON の SIMD を手書きする。** ブラシカーネルと細分割の内側ループはここで 2〜4 倍変わります。`float3` を素朴に扱わず、4 頂点まとめて処理する構造にしてください
- 浮動小数点の決定性が必要な箇所（Undo の再現）では、最適化フラグに注意する

## 2.7 UI フレームワーク（最大の未解決課題）

**C++ には、タブレット向けの production レベルな UI ツールキットが存在しません。** これがネイティブ路線で最も工数を食う部分です。正直に見積もってください。

| 候補 | 評価 |
|---|---|
| **自前 UI（レンダラ上に構築）** | **推奨。** サークルメニュー、ドッキング、精度調整スライダーはどのみち自作が必要。ならば全体を統一した方が良い。Nomad Sculpt もこの道 |
| RmlUi | MIT。HTML/CSS 風の retained UI。パネル類だけなら選択肢になる |
| Dear ImGui | MIT。**開発用デバッグオーバーレイ専用にしてください。** immediate mode は指操作の production UI には向きません |
| ネイティブ UI（UIKit / Android View） | テキスト入力、ファイルピッカー、システムダイアログ**だけ**に使う。UI 全体を載せると二重実装になる |

推奨する分担:

- ビューポート内のすべて（パネル、サークルメニュー、スライダー、ギズモ）= 自前描画
- テキスト入力、ファイル選択、システム共有シート = プラットフォームのネイティブ UI
- 開発中のデバッグ表示 = Dear ImGui（製品ビルドから除外）

テキスト描画には **HarfBuzz**（シェーピング）と **FreeType**（ラスタライズ）、または軽量に済ませるなら `stb_truetype` を使います。日本語対応を考えると HarfBuzz + FreeType が安全です。

## 2.8 プラットフォーム層

### iOS

- **Objective-C++（`.mm`）** で UIKit を橋渡しします。Swift は不要です
- `UIViewController` + `CAMetalLayer`（bgfx 経由）
- 入力は `UIResponder` の `touchesBegan/Moved/Ended` を直接受け、`coalescedTouches` と `predictedTouches` をそのまま使えます。**ここがネイティブの最大の恩恵です**
- ファイルは `UIDocumentPickerViewController` とセキュリティスコープ付き URL

### Android

- **`GameActivity`（Android Game Development Kit）を推奨します。** `NativeActivity` より入力の扱いが良く、`MotionEvent` をネイティブ側で直接受け取れます。スタイラスの軸情報（`AXIS_TILT`、`AXIS_ORIENTATION`）や履歴サンプルにアクセスできます
- Java 側のコードを最小限に抑えられます
- ファイルは Storage Access Framework。ここは JNI 経由が避けられません

### デスクトップ

- **SDL3**（zlib ライセンス）でウィンドウ、入力、イベントループを賄う
- **PC ビルドを初日から維持してください。** 実機ビルドを待たずに反復できるかどうかが開発速度を決めます。ネイティブ路線ではエディタが無い分、ここが生命線になります

## 2.9 ビルドとツールチェイン

| 項目 | 選定 |
|---|---|
| ビルドシステム | **CMake**（iOS は Xcode プロジェクト生成、Android は Gradle + NDK） |
| C++ 標準 | C++20。ただし例外と RTTI は無効化を検討（バイナリサイズと決定性のため） |
| 数学ライブラリ | GLM（MIT）または自前の SIMD 型 |
| テスト | doctest または Catch2。**`core/` のテストは必ず書いてください** |
| プロファイラ | **Tracy**（BSD-3）。モバイル対応で、フレーム内訳の可視化に極めて優秀。最初に入れる |
| クラッシュレポート | Sentry Native または Crashpad |
| 圧縮 | zstd（BSD）。プロジェクトファイル用 |
| 依存管理 | vcpkg か、submodule で固定。**依存は最小限に保つ** |

## 2.10 Undo / Redo 設計

「一つ進む・一つ戻る」ボタンを常時表示するため、Undo は全モード共通の単一スタックにします。**後から直すのが極めて困難なので、最初に設計してください。**

コマンドパターンとリージョンスナップショットの併用です。

| 操作 | 記録方法 | 概算サイズ |
|---|---|---|
| スカルプトストローク | 触れた BVH リーフの座標差分のみ | 1〜10MB |
| 頂点移動 | 選択頂点の旧座標 | 数 KB |
| トポロジ変更（ベベル等） | 操作前メッシュの全体スナップショット | メッシュサイズ相当 |
| マスク編集 | 差分のランレングス圧縮 | 数百 KB |

専用のアリーナに確保し、上限（全体予算の 25% 程度）を超えたら古い履歴から破棄します。**タブレットではディスクへの退避は遅すぎるため、履歴段数は 30〜50 程度に制限するのが現実的です。**

## 2.11 レンダリング方針

- **スカルプトモード: マットキャップ（MatCap）シェーディング** — テクスチャ 1 枚のルックアップのみでライティング計算ゼロ。ZBrush と Nomad が採用している理由がこれで、モバイルでは決定的に軽くなります。標準にしてください
- **マテリアルモード: PBR（GGX + IBL）** — 事前フィルタ済みキューブマップで環境光
- **ワイヤーフレーム表示**: バリセントリック座標を使うシェーダで実装。高ポリでは重いので、一定ポリゴン数を超えたら自動で間引き表示にします
- **部分アップロード**: 頂点バッファを永続的に保持し、汚れた BVH リーフに対応する範囲だけを更新します。ネイティブなのでバッファのサブ範囲更新を直接呼べます。**これが「軽く動作する」の実現手段そのものです**

## 2.12 フレーム予算（60fps = 16.6ms）

数値目標を持たないと必ず重くなります。ストローク中の内訳目標:

| 処理 | 予算 |
|---|---|
| 入力処理・ストローク補間 | 1ms |
| ブラシ適用（並列 + SIMD） | 4ms |
| 法線再計算 | 2ms |
| BVH 更新 | 2ms |
| GPU 部分アップロード | 2ms |
| 描画 | 5ms |

Tracy を最初期に組み込み、この内訳を常時監視できるようにしてください。
