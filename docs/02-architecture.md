# 02. 技術スタックとアーキテクチャ

## 2.1 エンジン選定

リポジトリ名から Unity 前提と理解しました。この選択は妥当です。理由と注意点を挙げます。

**Unity 6 LTS + URP を推奨します。**

- 良い点: iOS / Android / Windows / macOS を単一コードベースで出せる。ネイティブプラグイン機構が枯れている。Burst コンパイラと Job System により、幾何演算を C++ に近い速度で書ける。
- 悪い点: `UnityEngine.Mesh` API は重く、GC が発生する。標準の入力システムはペンとタッチを十分に区別できない。→ どちらも回避策があります（後述）。

代替案を検討した結果:

- **ネイティブ C++（bgfx / 自前 Metal・Vulkan）** — 最速だが開発工数が 2〜3 倍。個人〜少人数では非推奨。
- **Godot 4** — ライセンスは魅力的だが、モバイルのペン入力とネイティブプラグイン周りが Unity より弱い。
- **Flutter / React Native** — 3D 編集アプリには不適。検討不要。

## 2.2 最重要のアーキテクチャ原則

> **ジオメトリカーネルを Unity から切り離す。**

`UnityEngine` に依存しない独立アセンブリ（asmdef）として幾何演算コアを作ります。依存してよいのは `Unity.Collections`、`Unity.Mathematics`、`Unity.Burst` だけです。

これによって得られるもの:

- ユニットテストがエディタ起動なしで走る（開発速度に直結）
- 将来 C++ に移植したくなったときの逃げ道が残る
- Unity のバージョンアップで壊れにくい

```
Assets/
  Core.Geometry/        # UnityEngine 非依存。メッシュ、細分割、ブラシ演算
  Core.Document/        # シーングラフ、Undo、プロジェクト保存
  Core.IO/              # ファイル入出力（ネイティブライブラリのラッパ）
  App.Rendering/        # URP 連携、シェーダ、描画チャンク管理
  App.Input/            # ジェスチャ調停、ペン/指/マウスの抽象化
  App.UI/               # パネル、ドッキング、サークルメニュー
  App.Modes/            # モデリング / UV / スカルプト / マテリアル
  Platform.iOS/         # Objective-C プラグイン
  Platform.Android/     # Java/Kotlin プラグイン
```

## 2.3 メッシュデータ構造

ハーフエッジ構造は理論的には美しいのですが、**モバイルではメモリ効率とキャッシュ効率が悪すぎます**。採用しないでください。

推奨する構造は、用途で 2 つに分けます。

### 編集用（モデリングモード、低ポリ）

構造体配列ではなく、配列の構造体（SoA）で持ちます。

```
positions   : NativeArray<float3>     頂点座標
faceOffsets : NativeArray<int>        面 i の頂点が faceCorners のどこから始まるか
faceCorners : NativeArray<int>        面を構成する頂点インデックス列
cornerUV    : NativeArray<float2>     コーナー単位の UV（頂点単位ではない）
edgeCrease  : NativeArray<half>       エッジのクリース値
```

隣接情報（頂点→接続面、エッジ一覧）は**派生データ**として CSR 形式で別途構築し、トポロジ変更時のみ再構築します。常時保持しないのがポイントです。

### スカルプト用（高ポリ、トポロジ固定）

トポロジが変わらないので、平坦な配列＋空間分割で十分です。

```
positions : NativeArray<float3>
normals   : NativeArray<float3>
bvh       : 三角形クラスタ単位の BVH（Blender の PBVH 相当）
```

**BVH のリーフ単位で「汚れフラグ」を持つことが性能の鍵です。** ブラシストロークで触れたリーフだけを再計算し、GPU にも部分アップロードします。全メッシュを毎フレーム再アップロードすると、100 万ポリで即座に破綻します。

## 2.4 GPU への部分アップロード

Unity で最も効きます。`Mesh` を毎回作り直すのではなく:

```csharp
// GraphicsBuffer を直接持ち、変更範囲だけ書き換える
vertexBuffer.SetData(dirtyPositions, srcOffset, dstOffset, count);
```

`GraphicsBuffer` ＋頂点プリング（シェーダ側で `StructuredBuffer` から読む）にすると、Unity の Mesh API のオーバーヘッドを完全に迂回できます。**これが「軽く動作する」の実現手段そのものです。**

## 2.5 レンダリング

- **スカルプトモード: マットキャップ（MatCap）シェーディング** — テクスチャ 1 枚のルックアップのみでライティング計算ゼロ。ZBrush と Nomad が採用している理由がこれで、モバイルでは決定的に軽くなります。標準にしてください。
- **マテリアルモード: PBR（GGX ＋ IBL）** — 事前フィルタ済みキューブマップで環境光。
- **ワイヤーフレーム表示**: バリセントリック座標を使うシェーダで実装。ただし高ポリでは重いので、一定ポリゴン数を超えたら自動で非表示か間引き表示にします。
- **API**: iOS は Metal、Android は Vulkan（GLES3.2 フォールバック）。**ジオメトリシェーダは使わないでください**（Metal に存在しません）。

## 2.6 Undo / Redo 設計

「一つ進む・一つ戻る」ボタンを常時表示するとのことなので、Undo は全モード共通の単一スタックにします。ここは後から直すのが極めて困難なので、最初に設計してください。

方式はコマンドパターンとリージョンスナップショットの併用です。

| 操作 | 記録方法 | 概算サイズ |
|---|---|---|
| スカルプトストローク | 触れた BVH リーフの座標差分のみ | 1〜10MB |
| 頂点移動 | 選択頂点の旧座標 | 数 KB |
| トポロジ変更（ベベル等） | 操作前メッシュの全体スナップショット | メッシュサイズ相当 |
| マスク編集 | 差分のランレングス圧縮 | 数百 KB |

メモリ上限を設け（例: 全体予算の 25%）、超えたら古い履歴から破棄します。**タブレットではディスクへの退避は遅すぎるため、履歴段数は 30〜50 程度に制限するのが現実的です。**

## 2.7 フレーム予算（60fps ＝ 16.6ms）

数値目標を持たないと必ず重くなります。ストローク中の内訳目標:

| 処理 | 予算 |
|---|---|
| 入力処理・ストローク補間 | 1ms |
| ブラシ適用（Burst 並列） | 4ms |
| 法線再計算 | 2ms |
| BVH 更新 | 2ms |
| GPU 部分アップロード | 2ms |
| 描画 | 5ms |

プロファイラで常時この内訳を監視できる開発用オーバーレイを、最初期に作っておくことを勧めます。
