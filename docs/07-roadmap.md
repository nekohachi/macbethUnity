
# 07. ロードマップとリスク

## 7.1 フェーズ 0: 技術検証（最優先・4〜6週間）

**UI を一切作らずに、危険な部分だけを先に潰します。** ここを飛ばして UI から作り始めると、後で全部作り直しになります。

各スパイクには「合格ライン」を設定し、達成できなければ設計を見直します。

| スパイク | 検証内容 | 合格ライン |
|---|---|---|
| **0. 土台の立ち上げ** | CMake、bgfx、iOS / Android / PC の 3 ビルド、Tracy 導入。三角形 1 枚を全プラットフォームで表示 | 3 環境でビルドが通り、CI で自動化されている |
| **A. 入力** | iOS / Android でペンと指を区別し、筆圧・傾き・中間サンプル・予測入力を取得 | 実機でペン描画の遅延が 30ms 以下、ストロークがカクつかない |
| **B. スカルプト性能** | 200万トライアングルにブラシを適用し、部分 GPU アップロードで描画 | ストローク中に 60fps 維持、フレーム予算内 |
| **C. マルチ解像度** | OpenSubdiv 組み込み。低レベル編集→高レベルのディテール保持の往復 | `03-multires-core.md` の 6 項目すべて達成 |
| **D. ファイル入出力** | ufbx で FBX 読み込み、OBJ / FBX / USD 書き出し | Maya と ZBrush で開いて破綻しないこと |
| **E. メモリ** | 実機で長時間の編集セッション。Android 中位機での挙動 | メモリ予算内に収まり、強制終了しない |

**スパイク C が本アプリの生命線です。** ここが通らないなら、コンセプトごと考え直す価値があります。

ネイティブ C++ を選択したため、スパイク 0（土台の立ち上げ）が追加されています。ここに 2〜3 週間かかりますが、**スパイク B〜D は `core/` の中だけで完結するので、デスクトップ上で先行して進められます**。土台の立ち上げと並行させてください。

## 7.2 フェーズ 1: アプリケーション基盤（14〜18週間）

エンジンを使わないため、この段階が最も重くなります。ここがネイティブ路線の主なコスト増分です。

- **UI フレームワークの自作**（`02-architecture.md` 2.7）— パネル、レイアウト、テキスト描画、ヒットテスト。**この項目だけで 6〜8 週間を見込んでください**
- ドキュメントモデル、シーングラフ
- **Undo / Redo（全モード共通、最初に作ること）**
- モードタブと切り替え機構
- カメラとジェスチャ調停層
- サークルメニュー、修飾キーラッチ、左側固定コントロール
- ドッキング可能なパネルシステム
- プロジェクトの保存・読み込み（独自形式）
- **PC ビルドの維持**（エディタが無い分、開発速度の生命線）

この時点で「何もできないが、操作は気持ちいい」状態を作ります。**操作感の評価はここで一度実機で行ってください。**

## 7.3 フェーズ 2: スカルプトモード v1（10〜12週間）

マルチ解像度が中核なので、モデリングより先にスカルプトを作ります。

- ブラシ 11 種、アルファ、ストロークタイプ、筆圧カーブ
- マスキング一式、対称
- サブディビジョンレベルとディバイドスライダー
- マットキャップ表示

## 7.4 フェーズ 3: モデリングモード v1（10〜12週間）

- 選択（4モード）、ソフト選択、タッチ用ギズモ
- 編集ツール一式（`05-modes.md` の表）
- クリース設定
- **マルチ解像度ブリッジの完成** — トポロジ非変更ツールでの高レベル保持

**フェーズ 2 と 3 が完了した時点が、最初のリリース候補です。** ここで一度外部ユーザーに触ってもらってください。

## 7.6 期間の現実的な見積もり

上記を単純に足すと、**フルタイム 1 人で v1.0（フェーズ 0〜3）まで約 12〜15 か月**です。ただしこれは順調にいった場合で、実際にはこの手のアプリでは 1.5〜2 倍になるのが普通です。

ゲームエンジンを使う場合の見積もりは 8〜10 か月でした。**差分の 4〜5 か月がネイティブ C++ を選んだ代価**で、その大半は UI フレームワークとプラットフォーム層の自作に消えます。この代価と引き換えに、メモリ制御、フレーム時間の一貫性、入力遅延という本アプリの核心的な価値を得ます。

比較として、率直な数字を挙げます。

- **Nomad Sculpt** — 個人開発、5 年以上。スカルプトに絞ってこの期間
- **Substance Painter** — Allegorithmic の専任チームで数年、その後 Adobe が継続開発
- **ZBrush for iPad** — Maxon が既存の ZBrush 資産を持った状態で数年

**全部入りを目指さず、v1.0 をスカルプト＋モデリング＋マルチ解像度に絞ることが、完成させる唯一の道だと考えます。**

## 7.7 リスク一覧

| リスク | 深刻度 | 対策 |
|---|---|---|
| **マルチ解像度が性能要件を満たせない** | 致命的 | フェーズ 0 スパイク C で最優先検証。差分更新の実装で対処 |
| **Android のメモリ不足で強制終了** | 高 | メモリ予算を設計に組み込む。超過時の自動レベル低下。端末別プロファイル |
| **UI フレームワークの自作が想定より膨らむ** | 高 | ネイティブ路線で最も見誤りやすい箇所。パネルは最小限から始め、ドッキングは後回しにできる設計にする |
| **C++ / グラフィックスの習熟不足** | 高 | 着手前にスキルを正直に評価する。不足するならエンジン利用に戻す判断を早期に |
| **`.mb` / Substance 非対応でユーザーが失望する** | 中 | 「対応していない」ではなく「`.ma` 経由」「テクスチャ書き出し経由」と代替手順を明示的に案内する。ストア説明文にも明記 |
| **GPL コードの混入** | 中 | Blender のコードを一切参照しない。使用ライブラリのライセンスを一覧管理する（MIT / Apache / BSD のみ採用） |
| **開発期間が想定を超える** | 高 | スコープを削る判断を早めに。UV とマテリアルは切り離し可能に設計しておく |
| **グラフィックス抽象（bgfx）の制約に突き当たる** | 低 | `gfx/` 層の内側に閉じ込め、漏らさない。差し替え可能に保つ |
| **競合の先行** | 中 | マルチ解像度ブリッジという明確な差別化があるので、そこに集中する |

## 7.8 いま決めるべきこと

**決定済み: 実装はネイティブ C++。** ゲームエンジンは使いません（`02-architecture.md` 2.1）。

残る未決事項:

1. **グラフィックス抽象は bgfx か Dawn か** — bgfx を推奨。Web ビューアを戦略的に重視するなら Dawn
2. **開発体制** — 1 人か、複数人か。期間見積もりが大きく変わります
3. **v1.0 のスコープ** — 本ドキュメントの提案（スカルプト＋モデリング＋マルチ解像度）で合意できるか
4. **収益モデル** — 買い切りかサブスクか。これは UI 設計（機能制限の出し方）に影響します
5. **どちらのプラットフォームを先に出すか** — iPad 先行を推奨します。端末の種類が少なく性能が高いため、開発とテストの負担が段違いに小さくなります
6. **リポジトリ名** — `macbethUnity` は実態と合わなくなりました。改名を検討してください

## 7.9 最初に着手すべき具体的なタスク

2 系統を並行して進めるのが最も効率的です。

**系統 1（デスクトップ上、グラフィックス不要）** — 今すぐ着手できます。

- `core/geometry` の骨格を作る
- OpenSubdiv を組み込む
- **スパイク C（マルチ解像度）を `core/` 内で完結させて検証する。** `03-multires-core.md` 3.5 節に手順があります
- doctest でテストを書きながら進める

**系統 2（プラットフォーム層）**

- スパイク 0: CMake + bgfx で iOS / Android / PC の 3 ビルドを通す
- スパイク A: 入力層。ペンと指の判別、`coalescedTouches` / `predictedTouches`

**スパイク C と A が本アプリの成否を決めます。** 系統 1 はグラフィックスもプラットフォームも要らないので、土台の立ち上げを待たずに今日から始められます。ここから着手することを勧めます。
