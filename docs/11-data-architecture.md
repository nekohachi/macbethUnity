# 11. データ設計（保持、受け渡し、非破壊）

作成: 設計担当（Fable）。`10` の「土台」フェーズで実装担当（Opus）が従う設計。

## 要件

| # | 要件 | 出どころ |
|---|---|---|
| R1 | PC 版とタブレット版でデータの受け渡しが簡単で、データが保持される | ユーザー |
| R2 | Maya と受け渡せる。できれば ZBrush と Substance Painter とも | ユーザー |
| R3 | スカルプトとテクスチャをなるべく非破壊で調整でき、往復できる構造 | ユーザー |

## 結論

1. **作業用の形式は自前の `.mbz`**（zip の中に JSON とバイナリ）。USD の概念に 1 対 1 で対応させて設計する
2. **PC とタブレットは同じ Web アプリ**なので、受け渡しは `.mbz` ファイル 1 つで済む。まずはクラウドドライブのフォルダ経由、将来は任意で同期サーバー
3. **外部との受け渡しは USD を本命、FBX と OBJ を実務用**にする。マルチ解像度は外部に持ち出せないので、ベースメッシュ + ディスプレイスメントマップに焼く
4. **非破壊の構造は「破壊的なレベル 0 の上に、再評価できる層を積む」**。モデリングは Undo 付きの破壊編集、その上のサブディビジョン、スカルプトレイヤー、UV、ペイントレイヤーは全部データとして保持し、下が変わったら再評価する
5. **同じトポロジで戻ってきたら、ベースだけ差し替えて上の層を残す**。これが実務上の「往復」

以下、順に根拠と仕様。

---

## 1. 作業用形式 `.mbz`

### なぜ自前か

USD をそのまま作業用にする案も検討した。USD は n-gon、クリース、任意の primvar、レイヤー合成（非破壊そのもの）を持ち、Maya・Substance・Blender が読める。理想に近い。
しかし **OpenUSD をブラウザで動かすライブラリは重く、書き出しに欠けがある**（TinyUSDZ は読みが中心、Autodesk の wasm 版は巨大）。作業用形式を外部ライブラリの成熟度に賭けると、保存できない事故が起きる。

glTF を作業用にする案は、**四角形と n-gon を持てない**ので却下。ポリゴンモデラーの作業形式としては失格。

したがって作業用は自前で完全に制御し、**USD の概念にそのまま写せる形**に設計する。USD 書き出しは翻訳になる。

### 構造

```
name.mbz  (zip)
├ manifest.json        形式バージョン、アプリのバージョン、作成日時、サムネイルの参照
├ scene.json           オブジェクト階層、トランスフォーム、ピボット、表示設定、カメラのブックマーク
├ meshes/<id>.bin      レベル 0 のメッシュ（下記のバイナリ形式）
├ multires/<id>/L<n>.bin   レベル n の接空間デルタ（float16 × 3 × 頂点数）
├ layers/<id>/<layer>.json + .bin   スカルプトレイヤー（対象レベル、重み、デルタ）
├ uv/<id>/<set>.bin    UV セット（コーナー単位、複数可）
├ paint/<set>/<channel>/<layer>.png|.exr + layer.json   ペイントレイヤーとマスク、ブレンド設定
├ textures/            読み込んだ外部テクスチャ（Substance からの書き出しなど）
└ thumbnail.png
```

### メッシュのバイナリ形式

`02` のデータ構造そのまま。USD の `UsdGeomMesh` と同じ考え方（面ごとの頂点数 + 頂点インデックス列）。

| フィールド | 型 | USD での対応 |
|---|---|---|
| positions | float32 × 3 × V | `points` |
| faceCounts | uint32 × F | `faceVertexCounts` |
| faceCorners | uint32 × ΣfaceCounts | `faceVertexIndices` |
| edgeCrease | float32 × E（エッジは頂点ペアで特定） | `creaseIndices` / `creaseSharpnesses` |
| cornerSharp | float32 × V | `cornerIndices` / `cornerSharpnesses` |
| polygroup | uint16 × F | primvar `polygroup`（OBJ の `g`、ZBrush のポリグループ） |
| materialId | uint16 × F | `GeomSubset`（Substance のテクスチャセット） |
| vertexColor | uint8 × 4 × V（任意） | primvar `displayColor` |
| uv[set] | float32 × 2 × ΣfaceCounts（コーナー単位） | primvar `st`（faceVarying） |

**頂点の順序を安定させる**ことを仕様にする（書き出し・読み込みで並び替えない）。後述の「同じトポロジで戻ってきた場合」の判定に必要。

### 版管理

`manifest.json` の `formatVersion` を最初から入れる。読み込み時は古い版を新しい版へ変換する関数を版ごとに用意する（v1→v2→v3 と連鎖）。**版を上げるときは必ず変換関数を書く。** 後から足すのは地獄なので、最初の実装で仕組みを作る。

## 2. PC とタブレットの受け渡し（R1）

### 前提

PC 版とタブレット版は**同じ URL の同じ Web アプリ**。形式の変換は一切ない。受け渡しは `.mbz` を移動するだけ。

### 段階

| 段階 | 方法 | 状態 |
|---|---|---|
| 今 | 端末内の自動保存（localStorage） | 済み。ただし容量が小さく、端末をまたげない |
| 土台フェーズ | **自動保存を IndexedDB に移す**（数百 MB まで可）。`.mbz` の保存と読み込みを「ファイル」メニューに追加 | 必須 |
| 土台フェーズ | **クラウドドライブのフォルダを介する**。iPad は共有シートで「ファイル」App の iCloud Drive / Google Drive へ保存、PC の Chrome は File System Access API で同じフォルダを直接開く。Android は Storage Access Framework の選択ダイアログ | 必須。追加のサーバー不要 |
| v1.5 以降 | 任意の同期サーバー（ユーザー認証 + オブジェクトストレージ）。開くたびに最新を取得、保存のたびに送る | 任意。運用費と認証が要るので後回し |

### 注意

- iPad の Safari には File System Access API がないので、タブレット側は常に「共有シートで保存」「ファイル選択で読み込み」になる。これは制約として受け入れる
- `.mbz` は**複数プロジェクトを 1 端末に持てる**ように、IndexedDB 内に「最近のプロジェクト」一覧を持つ
- 自動保存と `.mbz` の関係: 自動保存は「作業中の状態のスナップショット」、`.mbz` は「名前を付けた保存」。Maya の autosave と Save と同じ関係

## 3. 外部との受け渡し（R2）

### 形式ごとに何が運べるか

| 内容 | OBJ | FBX | USD | glTF |
|---|---|---|---|---|
| メッシュ（四角形、n-gon） | ○ | ○ | ○ | ✕（三角形のみ） |
| 法線 | ○ | ○ | ○ | ○ |
| UV（複数セット） | △（1 セット） | ○ | ○ | ○ |
| クリース | ✕ | ✕ | **○** | ✕ |
| ポリグループ | ○（`g`） | △（マテリアル経由） | ○（primvar） | △ |
| マテリアル割り当て | ○（`usemtl`） | ○ | ○（GeomSubset） | ○ |
| 階層とトランスフォーム | ✕ | ○ | ○ | ○ |
| PBR マテリアルとテクスチャ | △（mtl） | △ | ○ | **○** |
| スキン・アニメーション（将来） | ✕ | ○ | ○ | ○ |
| マルチ解像度のレベル | ✕ | ✕ | ✕ | ✕ |

**マルチ解像度のレベルはどの形式でも運べない。** ZBrush も Maya も同じ制約で、業界の解は「ベースメッシュ + ディスプレイスメントマップ」。

### アプリごとの経路

| 相手 | 送る | 受け取る | 備考 |
|---|---|---|---|
| **Maya** | USD（クリース込み）、FBX、OBJ | FBX、OBJ、USD、`.ma`（限定） | USD が本命。FBX は誰でも持っている経路 |
| **ZBrush** | OBJ（`g` でポリグループ）、FBX | OBJ、FBX | ZBrush の内部形式は読めない。最新版は USD も読むが、ポリグループが運べるかは要確認 |
| **Substance Painter** | FBX か USD（UV + テクスチャセット = マテリアル割り当て必須） | 書き出されたテクスチャ（PNG / EXR） | Painter のレイヤーは受け取れない。テクスチャだけ |

### マルチ解像度の往復

| 方向 | 方法 |
|---|---|
| 出す | レベル 0 のメッシュ + ディスプレイスメントマップ（EXR、スカラーまたはベクター）+ 法線マップ。Maya も ZBrush も Painter もこの組み合わせを受け取れる |
| 戻す | 戻ってきたメッシュのトポロジがレベル 0 と一致していれば、**レベル 0 の座標だけ差し替えて上位レベルのデルタを残す**（下記 5 章）。一致しなければ上位レベルは破棄。ZBrush と同じ規則 |

ZBrush のレベルを直接受け取ることは、形式が非公開なので不可能。ここは最初から諦め、ユーザーには「ZBrush で作ったスカルプトは最高レベルのメッシュかディスプレイスメントとして受け取る」と案内する。

### Substance Painter との往復

1. 本アプリからメッシュ（UV とマテリアル割り当て付き）を FBX / USD で出す
2. Painter で塗り、テクスチャセットごとにチャンネルを書き出す
3. 本アプリで**テクスチャセットの命名規則を認識して自動で読み込み**、各チャンネルの「ベースレイヤー」として置く
4. 本アプリのペイントレイヤーはその上に積む

Painter のレイヤーは戻ってこないので、往復は「テクスチャ単位」まで。これが現実的な上限。

## 4. 非破壊の構造（R3）

### 原則

**モデリングは破壊的、その上は非破壊。**

Maya のようなコンストラクションヒストリは作らない（`05` で決定済み。モバイルでは重すぎ、実装コストも跳ね上がる）。代わりに、レベル 0 の上に積む層をすべてデータとして保持し、下が変わったら再評価する。

```
Object
├ Base            プリミティブのパラメータ | 読み込んだメッシュ | 編集済みメッシュ   ← レベル 0。破壊編集 + Undo
├ Multires        レベル 1..N の接空間デルタ                                 ← レベル 0 が動いても追従（03 章）
├ SculptLayers    レベルごとのデルタバッファ + 重み + 表示切替              ← 重みを変えれば再評価
├ UVSets          コーナー単位の UV、複数セット                              ← 頂点移動では壊れない
├ Materials       面ごとのテクスチャセット割り当て
└ PaintLayers     テクスチャセット × チャンネル × レイヤー（画像 + マスク + ブレンド + 不透明度） ← 書き出し時に合成
```

### 何が何に耐えるか

| 下で起きた変更 | Multires | SculptLayers | UV | PaintLayers |
|---|---|---|---|---|
| 頂点の移動（レベル 0） | 追従する | 追従する | 保持 | 保持 |
| トポロジ変更（ループ挿入、ベベル等） | **破棄**（再投影は v1.5） | 破棄 | ループ挿入は補間で保持、それ以外は要再展開 | UV が変わった面は要再ペイント |
| 別アプリから同じトポロジで戻る | 保持 | 保持 | 戻ってきた UV で上書き可 | 保持 |
| 別アプリから違うトポロジで戻る | 破棄 | 破棄 | 上書き | 破棄 |

**ループ挿入やベベルのときに UV を補間して保持する**のは実装コストが小さいので、モデリングのトポロジ操作は最初から UV を扱うように書く。後付けは難しい。

### ペイントの非破壊

Substance Painter と同じ考え方。レイヤーは画像として持ち、合成は表示時と書き出し時に行う。塗り直しは対象レイヤーだけを変える。マスクも画像。ジェネレータ（カーブチャ等）は v2 で、パラメータだけ保存して合成時に計算する。

## 5. 「同じトポロジで戻ってきた」判定

往復の要。以下をすべて満たしたら「同じ」とみなし、レベル 0 の座標だけ差し替える。

1. 頂点数が一致
2. 面数が一致
3. 各面の頂点インデックス列が一致（回転は許容しない。OBJ / FBX / USD は順序を保つ）

一致しなければ、ユーザーに「トポロジが変わっています。上位レベルとレイヤーを破棄して読み込みますか」と確認する。

そのために `.mbz` に**書き出し時のトポロジのハッシュ**を記録しておく。戻ってきたファイルのハッシュと比べれば、頂点数が同じでも並びが変わった事故を検出できる。

## 6. UV の置き場所（ユーザーの問い）

**結論: 独立した「UV」モードにする。今の 4 モード（モデリング / UV / スカルプト / マテリアル）のまま。**

| 案 | 判断 |
|---|---|
| モデリングに含める | UV 編集には 2D ビューポート、UV シェル単位の選択、展開・カット・縫合という別のツール群が要る。ツール列とマーキングメニューが二重になって混乱する |
| マテリアルに含める | Substance Painter が UV を編集できないのはそのため。UV はモデリングとペイントの間の工程で、両方から行き来する。マテリアルの下に隠れると導線が悪い |
| **独立モード** | Maya の UV エディタ、Blender の UV Editing ワークスペースと同じ。全ての DCC がこうしている理由は、編集対象と道具が違うから |

ただし境界は柔らかくする。

- UV モードは **2D ビューと 3D ビューを左右に並べ、選択を同期**する（`05` に記載済み）
- モデリングモードで面を選んだまま UV モードに入ると、対応するシェルが選ばれている
- モデリングモードに「自動 UV」と「チェッカー表示」だけは置く。単純なケースはモードを切り替えずに済ませる
- スカルプト前に UV を切っておく必要はない。UV はレベル 0 のデータなので、スカルプト後でも切れる

## 7. 土台フェーズへの反映

`10` の「1. 土台の作り直し」に以下を加える。

- [ ] `.mbz` の読み書き（zip は JSZip、バイナリは上記の形式、`formatVersion` と変換関数の仕組み）
- [ ] 自動保存を IndexedDB へ。最近のプロジェクト一覧
- [ ] PC の Chrome で File System Access API による直接保存。iPad は共有シート、Android は選択ダイアログ
- [ ] トポロジのハッシュを書き出し時に記録し、読み込み時に照合
- [ ] `core/` のメッシュ構造にクリース、ポリグループ、マテリアル ID、UV セットの欄を最初から持たせる（今は座標と面だけ）
- [ ] トポロジ操作（ループ挿入、押し出し）が UV を補間するように書く

外部形式は `10` の 4 章の順（OBJ 済み → FBX 読み込み → FBX 書き出し → USD 書き出し）。USD 書き出しは、この文書の対応表どおりに `.mbz` を翻訳する。
